# AI Team Workflow

## 運用品質 Review

Task 16、Task 17、Task 18 では、すべての AI agent が `docs/core/operational-quality-baseline.md` を適用します。

reviewer agent は次を確認します。

- 認可と tenant 分離
- API contract と request validation
- DynamoDB access pattern と GSI 影響
- least-privilege IAM
- UI の visible error / partial-error state
- deployment impact report
- verification command

このドキュメントは、TaskTree v2.0.0 改善のための AI エージェントチーム運用方法を定義します。

## 基本フロー

1. 要求をすぐに実装せず、まず作業目的と修正範囲を整理する。
2. その作業が v2.0.0 の目標である「実際のアプリ品質改善」に役立つかを確認する。
3. どのパッケージを修正する必要があるかを確認する。
4. Claude が主要機能実装または複雑な修正作業を行う。
5. GPT/Codex が実装結果を検証し、必要な補完パッチを行う。
6. セキュリティ、権限、型安全性、パッケージ境界違反がないかを確認する。
7. 必要なテストまたは再現手順を整理する。
8. 重要な設計判断はドキュメントに反映する。

## モデル使用基準

### GPT/Codex

主に検証、レビュー、テスト、補完修正に使用します。

- Claude 実装結果の検証
- コードレビュー
- バグ修正および補完パッチ
- テスト作成
- type-check、lint、test 実行
- ドキュメント更新
- レビューフィードバック反映
- 小さな補助実装

### Claude

主に主要機能実装と複雑なコード修正に使用します。

- 機能実装
- 複雑なリファクタリング
- 既存コードの流れを踏まえた修正
- 要件整理
- UX フロー確認
- 大きな変更前の実装計画
- エッジケース探索

### Gemini

主に広範囲分析、アイデア拡張、方針比較に使用します。

- コードベース要約
- 機能アイデア拡張
- 実装方針比較
- プロダクト上の不足点発見
- 大きな範囲のドキュメント確認

## トークンと役割分担基準

- Gemini Flash はトークンに余裕があるため、広範囲分析、要約、アイデア拡張に使用する。
- Claude はコーディング能力が高いがトークン消費が大きいため、主要実装に集中して使用する。
- GPT/Codex は性能とトークン余裕のバランスが良いため、検証、テスト、補完修正に使用する。

## Claude Agent Teams の使用基準

Claude Agent Teams は、Claude 内部で複数の teammate を動かすための手段です。

TaskTree では、Claude Agent Teams を常用してはなりません。大きく、並列化する価値がある作業に限定して使用します。

使用する場面:

- 複数パッケージにまたがる機能実装
- フロントエンド、API、テストを分担して進める大きな変更
- 認証、組織階層、権限、DynamoDB 設計に関わる変更
- 大規模レビュー
- 複数の原因仮説を並行して調査するデバッグ

使用しない場面:

- 小さな docs 修正
- README 修正
- 単一コンポーネント修正
- 単一 API handler の小さな修正
- 同じファイルを複数人で触る可能性が高い作業

推奨チーム分担:

- lead: 全体方針、作業分解、最終統合
- frontend: `task-app` と `task-ui` の影響調査
- core-api: `task-core` と `task-api` の影響調査
- infra: `task-infra`、AWS リソース、IAM 影響調査
- reviewer: パッケージ境界、権限、型安全性、テスト不足の確認

重要ルール:

- Agent Teams はトークン消費が大きいため、使用理由を必ず明確にする。
- teammate ごとに担当ファイルまたは担当範囲を必ず分ける。
- 同じファイルを複数 teammate が同時に編集してはならない。
- 大きな変更では、まず調査と計画に使用し、すぐに実装へ入らない。
- Claude Agent Teams の結果は、最終的に GPT/Codex で検証する。

## Repomix ベースの分析フロー

大きな作業では、AI が先に `npx repomix --output repomix-output.xml` を実行し、最新のコードベース要約を生成できます。

推奨フロー:

1. 作業範囲が広いかを判断する。
2. 広い作業であれば、`npx repomix --output repomix-output.xml` を実行する。
3. `repomix-output.xml` で全体構造と修正候補ファイルを把握する。
4. 修正する元ファイルを必ず直接読み直す。
5. 元ファイルだけを修正する。
6. 必要な検証コマンドを実行する。
7. `repomix-output.xml` はコミットしてはならない。

注意:

- Repomix 結果物は地図であり、実際の基準は必ず元ファイルである。
- Repomix 結果物には機密情報が含まれる可能性があるため、リポジトリに上げてはならない。
- 小さなドキュメント修正や単一ファイル修正では、Repomix を省略してもよい。

## 作業単位

作業は、ユーザーが確認できる業務フロー単位に分けます。

小さく安全に進めることは重要ですが、API 1 本、ボタン 1 つ、画面 1 つだけで PR を分けすぎてはいけません。
API、service、UI、test、必要最小限の infra をまとめ、動作確認できる単位を 1 Task とします。

README は各小タスクの詳細ログではなく、まとまった成果単位で要約します。

良い作業単位:

- Case 詳細から task を作成し、配下 task 一覧で確認できるようにする
- History 自動記録と Comment 表示を Case 詳細に追加する
- STANDARD case 作成から REQUEST / task 分解までを一つの業務フローとして実装する
- OPEN case 公開、Claim request、承認/却下を一つの検証可能な流れとして実装する

悪い作業単位:

- ボタン 1 つだけ追加する
- API handler 1 本だけ追加して UI につながない
- README だけを毎 Task 詳細に増やし続ける
- UI 全体改善
- バックエンド全体リファクタリング
- 権限システム全面再設計
- インフラ全体整理

## 変更前の確認

AI は修正前に以下を必ず確認します。

- どのパッケージを修正する必要があるか
- パッケージ境界を越えるか
- API 契約が変わるか
- DynamoDB 構造が変わるか
- AWS リソースや IAM 権限が変わるか
- 既存のテストや検証コマンドがあるか

## レビュー基準

Reviewer は以下を優先して確認します。

- セキュリティ問題
- 権限検証漏れ
- データ破損の可能性
- パッケージ境界違反
- 型安全性の低下
- ユーザーフロー破綻
- テスト不足
- デプロイ影響の説明不足

## 禁止事項

- AI ごとに異なる開発ルールを作ってはならない。
- 共通ドキュメントと矛盾するモデル別ルールを作ってはならない。
- 関係のないファイルを同時に修正してはならない。
- 失敗したテストを隠してはならない。
- インフラ変更を軽く扱ってはならない。
- ポートフォリオ目的を理由に、実際のアプリ品質を諦めてはならない。
