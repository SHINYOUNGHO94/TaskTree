# AI Coding Principles

## 運用品質基準

Task 16、Task 17、Task 18 は `docs/core/operational-quality-baseline.md` にも必ず従います。

残りの v2 作業では、認可、tenant 分離、IAM、DynamoDB access pattern、UI error state、deployment impact を第一級の coding concern として扱います。

このドキュメントは、TaskTree で作業するすべての AI エージェントが従うべき共通コーディング原則です。

## 1. 実装前に理解する

AI はコードを修正する前に、必ず現在の構造を理解しなければなりません。

- 要件が曖昧な場合は、必ず前提を明示する。
- アーキテクチャ、データモデル、セキュリティ、デプロイに影響する判断は、必ず先に確認する。
- 複数の方法がある場合は、必ずメリットとデメリットを説明する。
- 大きな変更を提案する前に、既存コードの意図を必ず把握する。

## 2. シンプルな解決を優先する

現在の作業を解決する最小の実装を優先します。

- 推測による機能追加をしてはならない。
- 一度しか使わない抽象化を作ってはならない。
- 今必要ではない設定可能性を追加してはならない。
- 解決策が大きくなりすぎた場合は、より単純な方法を必ず再検討する。

## 3. 小さく変更する

変更は必要な範囲に限定します。

- 修正対象パッケージの既存スタイルを必ず守る。
- 関係のないリファクタリングをしてはならない。
- 不要なフォーマット変更をしてはならない。
- 現在の変更によって生まれた不要コードだけを削除する。
- 別の問題を見つけた場合は、黙って修正せず、別の提案または課題として扱う。

## 4. 目標と検証を明確にする

すべての作業には完了条件が必要です。

- 実装前または実装中に、「完了」の条件を明確にする。
- 可能な場合は、テストまたは再現可能な検証手順を用意する。
- 関連する type-check、lint、build、test を実行する。
- 検証できない場合は、その理由を必ず説明する。

## 5. パッケージ境界を守る

TaskTree は TypeScript モノレポです。

- `task-app` は Next.js の UI と画面フローを担当する。
- `task-core` は共有型、認証、API 呼び出しサービス層を担当する。
- `task-api` は Lambda handler、repository、DynamoDB record 変換を担当する。
- `task-infra` は AWS CDK インフラ定義を担当する。
- `task-ui` は再利用可能な UI コンポーネントと theme を担当する。

明確な理由なしに、パッケージ境界を越えてはなりません。

## 6. 安全に自動化する

AI は多くの変更を自動で行えるため、必ず慎重に扱います。

- ユーザーが作成した可能性のある変更を戻してはならない。
- 大規模な削除、ファイル移動、インフラ変更は、必ず先に影響範囲を説明する。
- シークレット、トークン、個人情報、デプロイ成果物をコミットしてはならない。
- 失敗したコマンドやテスト結果を隠してはならない。

## 7. Repomix 使用原則

AI は、大きな作業や構造把握が必要な作業では `npx repomix` を積極的に活用します。

Repomix を使う目的は、プロジェクト全体を無作為に検索するのではなく、圧縮されたコードベース情報を先に確認し、トークンの浪費を減らすことです。

以下の場合は、作業前に `npx repomix --output repomix-output.xml` の実行を優先的に検討します。

- プロジェクト全体の構造把握が必要な作業
- 複数パッケージに影響する作業
- `task-app`、`task-core`、`task-api`、`task-infra` が同時に関係する作業
- 既存構造を知らない状態で機能追加する作業
- 大きなリファクタリング、権限変更、データモデル変更

以下の場合は、Repomix を省略してもよいです。

- 修正対象ファイルが明確な小さな変更
- README または docs のみの修正
- 単一コンポーネントの小さな UI 修正
- 同じセッションで既に最新構造を把握している連続作業

Repomix 使用時は、以下のルールを必ず守ります。

- `repomix-output.xml` は読み取り専用の分析資料としてのみ使用する。
- 実際の修正は必ず元のソースファイルに行う。
- 修正対象が決まったら、必ず対象の元ファイルを再度読んでから修正する。
- `repomix-output.xml` を直接編集してはならない。
- `repomix-output.xml` をコミットしてはならない。
- Repomix の結果が古い可能性があるため、最終判断は必ず元ファイルを基準にする。
